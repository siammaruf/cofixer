1. EXECUTIVE SUMMARY
Cofixer is a modern AI Agency & Technology full-stack web application with three parts: (1) a unified Frontend React 19 SPA with SSR for public pages, serving both the dynamic public website AND the admin dashboard CMS, (2) a NestJS v11.1.21 REST API Backend, and (3) PostgreSQL 18 + Redis 8 data layer. The public frontend is FULLY DYNAMIC - all content (services, projects, blog posts, team members, testimonials, FAQs, SEO metadata) is loaded from the API and rendered server-side for SEO. The admin dashboard (/dashboard) acts as a complete CMS where authenticated users can create, edit, and manage all frontend content in real-time. Authentication uses AES-256-GCM encrypted JWT in httpOnly cookies with CSRF protection. No tokens are ever stored in localStorage. Fully responsive and production-ready.

3. SYSTEM ARCHITECTURE
Three-Part Architecture Cofixer is architected as three components: ONE frontend app with SSR for public SEO pages and SPA for the admin CMS dashboard, ONE backend API, and ONE database layer. All frontend content is DYNAMIC - loaded from the API. There is no hardcoded content. The dashboard is a full CMS where admins manage every aspect of the public website.
Part A: Frontend + Dashboard (Unified React with SSR) · Public Pages (/, /about, /services, etc.): Server-side rendered (SSR) for SEO · Data Loading: React Router 7 loaders fetch API data BEFORE rendering HTML · Meta Tags: Dynamic <title>, <meta>, JSON-LD rendered on server per request · Dashboard (/dashboard/*): Client-side SPA with auth guards, no SSR needed · All Content Dynamic: Hero text, service cards, project gallery, blog posts, team profiles, testimonials, FAQs - everything comes from API/database · Zero Hardcoded Content: No static text, no static images, no static links in frontend code
Part B: Backend API (NestJS) · Standalone service exposing JSON REST APIs consumed by frontend loaders · Cookie domain: Shared between frontend and API for httpOnly cookie auth · CMS API Endpoints: Full CRUD for all content types (services, projects, blog, team, etc.) · SEO API Endpoints: /api/v1/seo/settings, /api/v1/sitemap, /api/v1/robots-txt · Base patterns: BaseEntity, BaseRepository, BaseService, BaseController for ALL features
Part C: Data Layer · PostgreSQL 18: All relational data including CMS content and SEO settings · Redis 8: Token blacklist, CSRF store, API cache, rate limiting

6. SEO ARCHITECTURE (Server-Side Rendered)
Why SSR is Required For the public website to be SEO-friendly and rank on search engines, it MUST serve pre-rendered HTML with all content and meta tags. Search engine crawlers cannot execute JavaScript to wait for client-side data fetching. React Router 7 SSR solves this by rendering HTML on the server with all dynamic content already included.
SSR Strategy · Public Pages: SSR with React Router 7 loaders - HTML rendered server-side · Dashboard: Client-side only - no SSR needed (not indexed by search engines) · Data Fetching: Loaders fetch API data BEFORE React renders anything · Meta Tags: Rendered in <head> on server, visible to crawlers immediately · Structured Data: JSON-LD injected server-side in HTML

8. AUTHENTICATION & SECURITY

No Client-Side Token Storage · localStorage: NEVER used for auth tokens or session data · sessionStorage: NEVER used for auth tokens or session data · IndexedDB: NEVER used for auth tokens or session data · Cookies: Only httpOnly Secure cookies managed by the browser

Global JWT Guard + @Public() Decorator

// app.module.ts providers: [
{ provide: APP_GUARD, useClass: JwtAuthGuard,
}, ],

// Global: all routes protected by default

// Public routes use @Public() decorator @Public() @Get('services') async findAll() { ... }

// Admin routes protected by default + RBAC @AdminOnly() @Post('admin/services') async create(...) { ... }

RBAC with Composite Decorators

@Public() @AdminOnly() @AdminOrOwner() @ModeratorOrAdmin() @RequireRoles(...)

-> Bypass authentication -> Admin role required -> Admin OR resource owner -> Moderator or Admin -> Custom role combination

// Editor can manage content but not users/settings @RequireRoles(RolesEnum.ADMIN, RolesEnum.EDITOR) @Post('admin/blog') async createPost(...) { ... }
Encrypted httpOnly Cookie Authentication · Algorithm: AES-256-GCM authenticated encryption · Cookie Format: base64(iv + ciphertext + auth_tag) · Backend decrypts cookie on every request before JWT validation · Even if cookie is stolen, attacker cannot use it without encryption key
